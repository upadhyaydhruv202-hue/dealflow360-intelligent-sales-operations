# Database module

## Purpose

Reusable PostgreSQL persistence for the starter kit: one ORM (Prisma), connection pooling, migrations, seeding, transactions, and a repository layer with safe pagination, sorting, and filtering.

Identity tables (`users`, `roles`, `permissions`) and `refresh_tokens` support the Auth and RBAC modules. See [auth.md](auth.md) and [rbac.md](rbac.md). Document intelligence adds `documents` (source metadata) and `document_extractions` (AI output). See [documents.md](documents.md). Optional RAG adds `rag_documents` and `rag_chunks` (unused unless `FEATURE_RAG` is on). See [rag.md](rag.md). Optional search adds `search_documents` (unused unless `FEATURE_SEARCH` is on; generated `search_vector` lives in SQL only). See [search.md](search.md). Optional analytics adds `analytics_facts` (unused unless `FEATURE_ANALYTICS` is on; queries always filter `kpi_key` plus a bounded `occurred_at` range). See [analytics.md](analytics.md). Optional anomaly findings live in `anomaly_findings` (unused unless `FEATURE_ANOMALY_DETECTION` is on). See [anomaly.md](anomaly.md). Automation adds `automation_rules`, `automation_executions`, and `automation_action_runs`. See [automation.md](automation.md). Notifications add `notification_deliveries` and `notification_preferences` beside the in-app `notifications` inbox. See [notifications.md](notifications.md). Audit events live in `audit_events`. See [audit.md](audit.md).

## Architecture

```text
Controller / Service
        │
        ▼
   Repository
        │
        ▼
 Prisma Client (pooled)
        │
        ▼
    PostgreSQL
```

- **Prisma** is the only query/ORM layer. Do not add `pg`, Knex, Drizzle, or a second ORM.
- Repositories own queries. Services must not contain repetitive raw database logic.
- Controllers must not query Prisma or SQL directly.

## Schema conventions

| Rule | How it is applied |
| --- | --- |
| Primary keys | UUID, generated by PostgreSQL `gen_random_uuid()` |
| Foreign keys | Declared on relations; `ON DELETE CASCADE` for join tables and notifications |
| Unique constraints | `users.email`, `roles.name`, `permissions.key` |
| Not-null | Required scalars are non-optional in Prisma |
| Check constraints | Added in SQL migrations (Prisma 6 does not model `CHECK` in schema) |
| Timestamps | `createdAt` (`created_at`) and `updatedAt` (`updated_at`) on entity tables |
| Naming | Prisma camelCase, PostgreSQL snake_case via `@map` / `@@map` |

Check constraints currently enforce:

- emails stored lowercase with a basic `user@host.tld` shape
- role names lowercase
- permission keys like `users.read`
- non-empty bounded title/body/display name lengths
- password hashes long enough to be hashes, not placeholders of a few characters

## Indexing principles

Create indexes for real access paths, not for every column.

Index when you will:

- look up by a unique key
- filter in `WHERE`
- join on a foreign key
- order by a column together with a filter (composite index)

Current indexes:

- unique indexes on email, role name, permission key, and refresh token hash
- foreign-key indexes Prisma creates for relations
- `user_roles.role_id` and `role_permissions.permission_id` (the composite primary keys already cover the other side)
- `notifications (user_id, created_at)` for listing a user's notifications by time
- `notifications (user_id, read_at)` for unread counts
- unique `notification_deliveries.idempotency_key` for duplicate event suppression
- `notification_deliveries (status, created_at)` and `(channel, status)` for delivery tracking
- unique `notification_preferences (user_id, category, channel)`
- `refresh_tokens (user_id)`, `(family_id)`, and `(expires_at)` for revocation and lookup
- `documents (user_id, created_at)` and `documents (status)` for listing a user's uploads
- unique `document_extractions.document_id` so each source document has at most one extraction row
- `rag_documents (created_at)` and `rag_chunks (document_id)` plus unique `(document_id, chunk_index)` for optional RAG
- unique `search_documents (index_name, document_id)`, GIN on generated `search_vector` / `filters`, and `pg_trgm` GIN on `title` / `keywords` for optional search
- unique `analytics_facts (source, event_id)`, composite `(kpi_key, occurred_at)`, partial `(owner_id, occurred_at)`, and GIN `dimensions jsonb_path_ops` for optional analytics
- `automation_rules (trigger, enabled, priority)` for matching enabled rules
- unique `automation_executions (rule_id, event_id)` for idempotent runs
- unique `automation_action_runs (execution_id, action_index)` for retrying individual actions
- `audit_events (user_id, created_at)`, `(action, created_at)`, `(resource, created_at)`, and `(created_at)` for listing and filtering the audit API

Do not add covering indexes "just in case." Measure first.

## Connection and pooling

`DATABASE_URL` is required in production. Prisma's built-in pool is configured from:

| Variable | Default | Prisma URL parameter |
| --- | --- | --- |
| `DATABASE_POOL_MAX` | `10` | `connection_limit` |
| `DATABASE_POOL_TIMEOUT_SECONDS` | `10` | `pool_timeout` |

Values already present in `DATABASE_URL` are left unchanged. `/ready` pings PostgreSQL with `SELECT 1` through the same Prisma client.

If you later put PgBouncer in front of Postgres, keep a direct URL for migrations (`directUrl` in the Prisma schema) and point the pooled URL at PgBouncer.

## Migrations

Schema and migrations live in `database/prisma`.

```bash
npm run db:migrate        # apply pending migrations (deploy)
npm run db:migrate:dev    # create/apply a migration in development
npm run db:generate       # regenerate Prisma Client
```

`db:migrate` is non-interactive and is what CI and production should run.

When you add a model:

1. Edit `database/prisma/schema.prisma`.
2. Run `npm run db:migrate:dev -- --name add_widget`.
3. If you need a `CHECK` constraint, add it to the generated SQL before applying, or in a follow-up SQL migration.
4. Create or extend a repository under `backend/src/repositories`.
5. Add tests.

## Seeding

```bash
npm run db:seed
npm run db:reset    # drop database, migrate, seed (destructive)
```

Seed data is **demo-only** and runs when `DEMO_MODE` is on (the default outside production). Production with `DEMO_MODE=false` still seeds the RBAC catalog and skips demo users. It is not a real credential set:

| Email | Role | Password |
| --- | --- | --- |
| `demo.admin@example.com` | admin | `demo-password` |
| `demo.manager@example.com` | manager | `demo-password` |
| `demo.staff@example.com` | staff | `demo-password` |
| `demo.user@example.com` | user | `demo-password` |

Also seeded: roles (`admin`, `manager`, `staff`, `user`) and the default permission catalog (`users.read`, `users.write`, `roles.read`, `roles.write`, `reports.generate`, `notifications.read`, `notifications.write`, `odoo.read`, `odoo.write`, `ai.use`, `copilot.use`, `intents.use`, `rag.use`, `documents.analyze`, `documents.read`, `automations.read`, `automations.write`, `automations.execute`, `jobs.read`, `admin.settings`). USER can log in but does not receive `odoo.read` or `odoo.write`. See [rbac.md](rbac.md).

Local `npm run dev` also upserts that catalog on startup when `DATABASE_URL` is set, so new default permissions appear without re-seeding. Production does not do this; run `npm run db:seed` there.

Never put production passwords, API keys, or personal data in seeds.

## Repositories and query helpers

`createRepositories(prisma)` returns:

- `users` — create/find/list/update; list supports pagination, whitelist sorting, whitelist filtering; `findByEmailForAuth` is the only method that returns `passwordHash`; `findByIdWithRoles` loads roles and the permission union for Auth and RBAC
- `refreshTokens` — hashed refresh tokens, rotation, and family revocation
- `roles` / `permissions` — RBAC catalog (create, list, assign role/permission)
- `notifications` — in-app inbox
- `notificationDeliveries` — outbound send status across channels
- `notificationPreferences` — per-user category/channel toggles
- `documents` — uploaded source metadata; `documentExtractions` — AI output for a document
- `automation` — rules, executions, and per-action runs
- `rag` — optional indexed documents and chunks (`FEATURE_RAG`)
- `anomaly` — optional statistical findings (`FEATURE_ANOMALY_DETECTION`)

Shared helpers:

- `parsePagination` — default page size 20, **maximum 100**, rejects invalid input
- `parseSort` — field whitelist only
- `parseFilters` — field/operator/type whitelist only; never pass client field names straight through to Prisma
- `withTransaction(prisma, fn)` — interactive transaction; thrown errors roll back

Safe querying rules:

- Use Prisma (parameterized). Do not concatenate SQL from user input.
- `$queryRaw` tagged templates only. Do not use `$queryRawUnsafe` with request data.
- Unknown sort/filter fields fail validation.

## How future modules add models

Keep hackathon **business logic** in `modules/problem`. Persistence for those features still goes through this PostgreSQL database:

1. Add models to `database/prisma/schema.prisma` (name them after the domain, not `ProblemThing` unless that is the actual name).
2. Generate a migration.
3. Add a repository under `modules/problem/src/<domain>/` that receives `host.prisma`.
4. Call the repository from a problem service. Do not query Prisma from controllers.
5. Cover unique constraints, foreign keys, and invalid filters in tests.

Prisma uses a single schema per database. Do not add MongoDB, SQLAlchemy, or a second Node ORM.

## Local setup

Docker publishes PostgreSQL on `localhost:5433` so it does not collide with a native install on 5432. `.env.example` already uses that port for host-based Node. Full Compose (`docker compose up --build`) points the API and worker at the `postgres` service instead. Data lives in `docker-data/postgres` (gitignored). See [docker.md](docker.md).

```bash
cp .env.example .env
npm install
npm run deps:up
npm run db:migrate
npm run db:seed
```

If PostgreSQL was already initialized before the test-database init script existed:

```bash
docker exec hackathon-postgres createdb -U postgres hackathon_test
```

## Tests

Copy `.env.test.example` to `.env.test` so backend integration tests use `hackathon_test` instead of wiping demo rows in `hackathon`.

```bash
npm run db:test:prepare
npm test -w backend
```

Without `DATABASE_URL` (and without `.env.test`), integration tests are skipped; unit tests for pagination, sorting, filtering, and error mapping still run. Persist users and related rows with `backend/tests/factories` instead of ad-hoc inserts. See [testing.md](testing.md).

## Dependencies

- `@prisma/client` / `prisma`
- `bcryptjs` (seed hashes only)
- PostgreSQL 16 (Docker Compose)

## Limitations

- Check constraints are maintained in SQL migrations, not in `schema.prisma`
- Pagination helpers are used by repositories; list HTTP endpoints come with later modules
